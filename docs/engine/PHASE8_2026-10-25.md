# Playback / score-following Phase 8 execution record

Date: 2026-10-25 (America/Vancouver).

Status: implementation, measurements and Phase 8 verification complete. Base: Phase 7 (`0fb3232f`). Physical-device
and static-release qualification remain Phase 9; no push or deployment is part of this work.

## Prepared playback

The native bridge now reuses a prepared model/track sequence while its score/excerpt object, committed-change
watcher, playback-options revision and SoundFont generation match. `Score::changesChannel()` resolves to the
master score's channel, so edits, undo and redo invalidate an excerpt as well. A different score/excerpt,
SoundFont replacement or options change forces fresh preparation. Only one sequence is retained. Destroying its
score releases it; stale stream handles retain the Phase 1 safety contract.

This removes repeated FluidSynth allocation, SoundFont setup and track/event setup from unchanged Play/seek.
Model and track construction, rather than PCM rendering, were the dominant native startup cost in the handoff.
Measurements below distinguish that native saving from actual browser click-to-scheduling time.

Reuse required four concrete state fixes; the PCM verifier retains exact byte comparisons:

1. Flush kills old voices rather than leaving their release tails in the next stream (upstream patch 0003).
2. Every new stream explicitly flushes track input handlers, including a seek to the already-current position.
   This is defensive: the mutation experiment found that mixer activation transitions also flush in the current
   lifecycle, so removing only this extra call is equivalent. The handoff's expectation that this mutation must
   fail was not borne out. The edit-watcher mutation is caught at the intended invalidation assertion.
3. A same-key Note On can queue a Note Off for an old, forcibly finished voice before FluidSynth collects it.
   That Note Off must not resurrect the finished voice into release (patch 0004).
4. New voice assignments reset the previous slot's pan/send interpolation amplitude. Otherwise a reused slot
   skips its first 64-sample ramp. This explained the remaining roughly `7.8e-6` difference; it was not accepted
   as a tolerance (also patch 0004).

A full WAV can end partway through a 512-frame block. Rendering that partial final block left FluidSynth's
internal cursor offset for the next reused stream. WAV rendering now advances a full block and writes only the
requested samples; WAV duration stays unchanged. The existing whole-WAV/stream sample-identity test passes.

`playbackDiagnostics()` reports per-stage preparation and first-batch timing, reuse, native ownership and WASM
heap capacity. `setPlaybackReuse(false)` is an A/B diagnostic switch that restores fresh preparation per start.
Stop/await browser playback before using it. These are local diagnostics and contain no score content.

## Idle work and live presentation

After a committed editor edit, preparation may run after a one-second quiet period, in a browser idle callback
where available, through the existing serialized engine queue. It does not run as part of initial score loading,
fetch a SoundFont, create a stream or schedule audio. Eligibility is checked again at queue execution. Play,
further edits, score replacement and unmount cancel queued work; retirement waits for native work already in
flight. Paused/active playback, hidden documents and pending options changes skip warmup. The native method also
refuses to supersede an active mixer. `localStorage['ots-playback-idle-warmup']='0'` disables this opportunistic work.

Presentation feature-detects `AudioContext.getOutputTimestamp()` and uses a valid context/performance timestamp
correspondence. Missing, stale, invalid or zero timestamps fall back to the reported output latency, or base
latency when output latency is unavailable. Latencies are not added together or subtracted twice. Scheduling
and click anchors remain on the context's scheduling clock. Animation remains local; it adds no worker RPC.

Visual timing controls in editor Playback settings and player controls independently adjust measure highlighting
and tracking cursor by ±500 real milliseconds in 5 ms steps. Positive means earlier. The trims are shared local
preferences, defaulting to zero over automatic output compensation. They do not change audio, saved notation,
seek semantics, playback speed, native options or exported-video frame timing. The onset experiment uses our own
PCM and isolated notes rather than borrowing an MP3 encoder-delay correction.

The editor also offers independent **Measure highlighting** (on by default) and **Notehead highlighting** (off by
default) toggles in Playback settings. Either, both or neither can accompany the tracking cursor; choices persist
locally. Measure shading uses the already-fetched native measure events/boxes and the measure lead; notehead
colouring uses native segment events/boxes and the cursor lead. The editor/player share cached SVG note geometry.
No additional worker requests are made per position tick or toggle. Drawing stays in the small canvas layer,
with measure DOM updates at measure boundaries and note colouring at segment boundaries. A playback-only CSS
class preserves the engraving's fill/stroke attributes, selection, saved notation and undo state. Page changes,
SVG replacement, Stop and unmount clear stale marks; paused/manual paging shows marks only on the sounding page.

The first fresh Bach context had an 8.55-second cold outlier, mostly before the open RPC (8.14 seconds), rather
than in native preparation (312 ms). It is retained in the raw sample and p95. This is a dev-server/headless
measurement with a small cold sample count, not a claim of a cold-start improvement. Normal-renderer warm-start
medians improved about 54% for Bach and 89% for men-base. Native reuse is not the whole browser critical path.

In these instrumented normal-renderer runs, each start reported two starvation/re-anchor callbacks in both modes.
Scheduled sources retained after Stop were zero; WASM heap capacity was 64 MiB for Bach and 275.375 MiB for
men-base in both modes. Heap capacity is not live allocation or an audio-buffer byte count. Warm Stop-to-worker-
fence medians/p95 were Bach fresh 342/473 ms vs reuse 447/651 ms, and men-base fresh 309/322 ms vs reuse 437/587 ms.
These UI-driven cancellation observations include Playwright dispatch, React/source cleanup and worker delivery;
reuse does not establish a cancellation improvement. Retained model/track memory and device cancellation remain
explicit Phase 9 checks. No shorter startup buffer or broader render horizon was adopted on this evidence.

A follow-up on the final editor (default measure shading on) interleaved three fresh and three reused warm starts
per score/rate. It removed per-source retention instrumentation and Playwright's Stop actionability wait. Each
observation lasts at least 1500 ms after first scheduling; the raw report includes its actual interval (longer
when the renderer is busy). Direct stop-command retirement is measured separately from UI dispatch.

| --- | ---: | ---: | ---: |
| Bach / normal | 291.6 / 114.8 ms | 1.0 / 1.2 ms | 5 / 4 |
| Men-base / normal | 937.4 / 79.7 ms | 1.3 / 1.4 ms | 6 / 5 |

This separates quick native/command cancellation from the earlier hundreds-to-thousands of milliseconds of UI
automation/renderer delay. It also limits the conclusion: reuse greatly improves normal-renderer warm startup,
but the slower simulation does not establish uniformly better latency or stability. In the original 24-context
matrix the simulated warm p50/p95 was Bach fresh 1846/2844 ms vs reuse 1319/1921 ms, and men-base fresh 2268/3038 ms
vs reuse 1972/3410 ms. Cold men-base p95 varied from 3943 ms fresh to 7760 ms reused (only three samples each).
Keep those adverse/noisy observations visible; do not use these results to remove buffers or claim slow-device
qualification. Phase 9 must qualify the complete UI, underruns and interactive cancellation on physical devices.

2/8/16 = 11.30 / 8.30 / 6.24; men-base = 20.46 / 14.53 / 14.83. Larger pulls amortize RPC but do not establish an
end-to-end scheduling/stability benefit. The scheduler-policy follow-up changes startup buffer and merging
independently, then tests a true first-chunk candidate (no buffer/merge, minimum one batch):

| Two-second idle scheduler window | Bach normal | Men-base normal | Bach 4x | Men-base 4x |
| --- | ---: | ---: | ---: | ---: |

| Zero added startup buffer, same merge/minimum | 4.4 ms | 4.7 ms | 8.7 ms | 7.5 ms |
| 200 ms startup buffer, same merge/minimum | 3.6 ms | 4.6 ms | 10.2 ms | 9.1 ms |

The original matrix's early `selection-first-chunk` label actually retained 500 ms merging and minimum three

Own-PCM onset, eight isolated A4 strikes per instrument, first sample above 2% of that strike's peak:

| Instrument | Median onset after event | Maximum |
| --- | ---: | ---: |
| Piano | 2.61 ms | 4.24 ms |
| Violin | 15.33 ms | 16.96 ms |

This includes block/event quantization and the instrument attack under the bundled SoundFont; it is not a device
measurement or a universal correction for all pitches/fonts. It does not support a fixed 60 ms correction.
Automatic output alignment plus zero default user trims avoids imposing one instrument's attack on every score.

The browser A/B disables idle warmup to isolate reuse. It records cold contexts and repeated starts, first-score
paint approximation, SoundFont readiness, worker/native preparation, first pull, first scheduling, cancellation,
underflows, retained browser sources and heap capacity. It also measures batches of 2/8/16 and a separate idle
warm-after-edit case. Separate scheduler runs execute the maintained scheduler with the selection defaults,
zero/200 ms startup buffers, and PCM merging disabled, changing one policy at a time. These use a two-second
window and cancellation after 400 ms; their underflow counts are not long-session qualification.
Dev compilation is warmed outside measured contexts. Renderer 4x CPU throttling is a
simulation, not physical slow-device qualification. Cold p50/p95 with three contexts are descriptive.

Selection's existing 600 ms startup buffer and 500 ms merge policy, full-playback batch size and the 20/10-second
render horizon remain unchanged. Changes to those defaults require equal-stability evidence on slow devices;
measuring RPC efficiency alone is insufficient to justify them.
