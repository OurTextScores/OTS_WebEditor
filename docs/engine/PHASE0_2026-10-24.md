## Timing baseline and limits

Reference host: Intel Core Ultra 7 155H, WSL Linux, Node v24.21.0, headless Chromium 143.0.7499.4; Bach fixture
`public/test_scores/bach_orig.mscz`, local default SF3. The “before” runs overlapped the fresh compiler workload;
the “after” runs overlapped lighter verification. These small samples are diagnostic baselines, not a controlled
speed comparison or a product SLA. No latency optimization was implemented.

| Measurement, median                                                  |     Before |      After |
| -------------------------------------------------------------------- | ---------: | ---------: |
| Native preparation, first stream in a fresh Node process (3 samples) |  593.75 ms |  410.32 ms |
| Native preparation, subsequent streams (12 samples)                  |  299.73 ms |  199.17 ms |
| Browser first click-to-first-scheduled-source (3 fresh contexts)     | 3,994.4 ms | 1,238.7 ms |
| Browser subsequent click-to-first-scheduled-source (3 contexts)      | 1,744.6 ms |   767.3 ms |

Node measurements exclude network, worker RPC, browser scheduling and device latency. Browser measurements use a
real worker/Web Audio, but serve the soundfont locally by route and include Playwright actionability and dev-server
effects. Scheduled preroll was 15 ms in the browser baseline; it is not an output-device latency estimate. The
reporting tools explicitly distinguish those scopes. Use controlled repeated device measurements before choosing
future buffer/model-cache changes.

## Scope and next step

This phase establishes build ownership and a measurable baseline. It does not implement native session safety,
partial-layout guards, preparation caching, tempo/repeat UI, contextual seeking or score following. Those remain
Phases 1 onward in the approved private design. Safari/mobile device checks belong to later rollout qualification;
the current browser evidence is headless Chromium.
